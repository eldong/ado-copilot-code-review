Enterprise readiness plan

Planning reference for issue #1: Enterprise Ready. Assessed November 2, 2026.

Proposal only. This document does not implement authentication changes, provision infrastructure, or authorize a migration.

Goal and recommendation

Run automated Azure DevOps pull request reviews without personal access tokens (PATs), without depending on an employee's identity or Copilot seat, and with company-owned billing and governance.

Recommended starting point: keep reviews in Azure Pipelines, use its existing job-token authentication for Azure DevOps, and evaluate the existing custom model provider mode with a company-owned model endpoint. This is the smallest architectural change if billing to the company's model provider, rather than to GitHub Copilot, is acceptable.

If GitHub-hosted Copilot models and organization-level Copilot billing are mandatory, evaluate a GitHub Actions execution backend instead. Do not assume that a generic GitHub App token or an Azure workload identity can authenticate Copilot directly in Azure Pipelines.

What already exists

  • Azure DevOps: useSystemAccessToken: true uses System.AccessToken as a bearer token. PAT authentication remains an alternative. The pipeline Build Service needs repository read access and Contribute to pull requests permission.
  • Default Copilot path: the task requires githubPat and exports it as GH_TOKEN. This authenticates as the token's user; replacing an employee with a shared account would not create a workload identity.
  • Custom provider path: useCustomModelProvider makes the GitHub PAT optional and accepts a provider endpoint, type, optional API key, and explicit model. Supported types in the task are openai, azure, and anthropic. Usage goes to the selected provider rather than a user's Copilot model allowance.
  • Current integration boundary: custom provider settings are passed through COPILOT_PROVIDER_BASE_URL, COPILOT_PROVIDER_TYPE, and COPILOT_PROVIDER_API_KEY. The task does not currently implement a federated model-provider token flow.
  • Agent permissions: the Copilot invocation permits all paths and tools and explicitly denies git push. That denial alone is not an enterprise isolation boundary.

Repository references: orchestration and authentication, task inputs, and configuration and permission guidance.

Separate the requirements

  • No PATs: achievable using the existing Azure job token and a custom model provider. A provider API key is not a PAT, but is still a long-lived secret.
  • No individual dependency: the model resource, credentials, permissions, and billing must belong to the organization, with administration independent of an employee's account.
  • No long-lived secrets: a stricter goal requiring workload federation or managed identity and a verified compatible model authentication path.
  • Central billing: company payment for user Copilot seats is different from automation usage attributed directly to the organization.

Architecture choices

Options to validate before implementation
OptionIdentity and billingWork and limitations
A. Azure Pipelines + company model provider Azure DevOps job token for PR operations; company-owned provider resource for model usage. No personal Copilot seat required for the custom-provider review path. Smallest starting point. Validate the installed CLI's provider configuration and model support. A company-managed API key can prove the no-PAT path, but does not meet a secretless requirement.
B. Azure Pipelines + federated model access Job token for Azure DevOps; an Azure service connection using workload identity federation, or an appropriate managed identity, for the model resource. Usage bills to the company's Azure resource. Requires implementation. Verify whether the chosen CLI/provider combination accepts and can refresh Microsoft Entra bearer tokens. If not, evaluate a narrowly scoped authenticated gateway or another model client; do not pass an Entra token as an API key without verifying protocol support.
C. GitHub Actions + organization-billed Copilot GitHub documents built-in GITHUB_TOKEN authentication with copilot-requests: write. In an organization-owned repository, usage is metered directly to that organization when its Copilot CLI organization-billing policy is enabled. Larger architectural change: execute the review in GitHub Actions, securely dispatch work from Azure DevOps, and return findings. The Actions token is not an Azure Pipelines credential or an Azure DevOps token. Cross-platform dispatch, repository-content transfer, and Azure DevOps result posting need a separate approved identity design.

Not a solution by itself: buying Copilot Business or Enterprise seats, renaming the PAT input, using a machine user's PAT, or substituting an arbitrary GitHub App installation token. None establishes a supported, user-independent Copilot authentication flow for this Azure Pipelines task.

Phased delivery plan

  1. Agree on the target

    Decide whether GitHub Copilot billing is mandatory or company-owned provider billing is acceptable; whether API keys are allowed or all credentials must be short-lived; and whether execution must remain in Azure Pipelines. Confirm Azure DevOps Services versus Server, agent hosting, network restrictions, model availability, and data residency requirements.

    Exit criterion: platform, security, and billing owners approve one architecture and its definition of “no personal dependency.”

  2. Prove the smallest no-PAT path

    In a non-production pipeline, enable useSystemAccessToken, expose the job token as required by the pipeline, and grant only the needed repository permissions. For option A, configure the existing custom-provider inputs with a company-owned endpoint, omit both PAT inputs, and select a model supporting tool calling and streaming.

    Verify compatibility with a specific CLI version before relying on current environment-variable configuration: current GitHub documentation describes provider configuration through providers.json and COPILOT_PROVIDERS_CONFIG. Identify any required adaptation rather than assuming old and current mechanisms are interchangeable.

    Exit criterion: a review reads a PR, posts a comment, updates an earlier automated thread, and records usage on the intended company billing resource with no PAT supplied.

  3. Implement only the selected authentication gap

    For option A, limit changes to verified provider compatibility, validation, and deployment documentation. For option B, add explicit federated authentication configuration, least-privilege model-resource access, short-lived token acquisition, and token refresh for long-running reviews. For option C, prototype the Actions backend and secure Azure DevOps handoff before modifying the extension's execution contract.

    Keep existing PAT mode available for compatibility unless deprecation is separately approved. Enterprise mode must fail clearly on missing or expired workload credentials; it must not silently fall back to a developer login, PAT, or different billing account.

    Exit criterion: repeatable unattended execution with the selected company identity and documented credential lifecycle.

  4. Apply enterprise guardrails

    Use isolated, preferably ephemeral agents; restrict tool access, filesystem scope, network egress, and credentials visible to the model process. Treat PR content as untrusted and do not expose privileged credentials to untrusted fork runs. Prefer deterministic comment posting outside the model process where practical.

    Approve provider retention, training, residency, and source-code handling policies. Pin and verify CLI releases, redact credentials and sensitive prompt content from logs, record correlation IDs and usage without unnecessary source content, and configure concurrency, timeout, and spend controls. Verify which budgets enforce limits versus merely send alerts. Clean up temporary credentials and provider configuration on success and failure.

    Exit criterion: security and cost owners approve the isolation, audit, data-handling, and incident-response design.

  5. Validate and roll out incrementally

    Use the existing TypeScript build and JavaScript/PowerShell test infrastructure. Add focused tests for the chosen authentication mode, missing credentials, expired tokens and renewal, forbidden access, secret redaction, cleanup, and absence of personal-credential fallback. Preserve regression coverage for PAT mode and existing review behavior.

    Run a sandbox integration review under the intended workload identity, verify actual billing attribution, and test that removing an employee's access does not stop the automation. Pilot on one repository, document permissions and operations, then expand with an explicit rollback to the last approved configuration.

    Exit criterion: all acceptance checks below pass before wider deployment.

Acceptance checklist

  • No Azure DevOps or GitHub PAT is configured in the enterprise deployment.
  • No employee's CLI login or Copilot seat is required for successful reviews.
  • Model usage appears on the approved company provider resource or GitHub organization's billing reports.
  • PR reads, comment creation, and automated thread updates work under least-privilege permissions.
  • If secretless operation is required, credentials are short-lived and long-running reviews handle renewal.
  • Invalid credentials fail without personal-identity fallback; logs and artifacts contain no credentials.
  • Untrusted PRs cannot obtain privileged tokens or execute unrestricted actions in a privileged environment.
  • Existing supported authentication paths continue to work, with documented migration and rollback procedures.

Verified external references
